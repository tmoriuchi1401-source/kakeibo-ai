# カテゴリ操作と支出明細の双方向リンク

PR #116 のリンク復旧と B:L の承認更新時の A 保持を引き継ぎ、生成処理を
`app/category_navigation.py` に共通化する。

- カテゴリ操作 A: H の固定支出IDを支出明細 A で完全一致検索する。欠落・重複IDは
  「代表取引を確認（ID不一致）」と表示し、リンクを生成しない。
- 支出明細 N: 「↩ カテゴリ操作に戻る」。対象は現在のカテゴリ操作の第1ブロックのみ。
  対象行がない場合は空欄、同じIDが複数行にある場合は明示した一覧リンクを表示する。
- 会計データ A:M、入力 C:F、固定条件キー、承認スナップショット、銀行確認欄を変更しない。
  行位置は数式の ROW と支出IDから毎回解決し、日付・金額をキーにしない。
- N の式は既存支出行にだけ設置する。代表でない取引では空欄となる。
  各行の式が同じなので A:M だけの並べ替えにも対応する。空のグリッド末尾には設置しない。
  明細追加時、明示的に導入済みの場合だけ新規行に同じ式を補完する。
- Sheetsアプリでリンクの行移動が機能しない端末では、リンクをSafariで開く。
  ID入力・検索は不要。実機での操作確認はPCの確認と区別して記録する。

## 導入・検証

`Category navigation UI maintenance` は既存の `kakeibo-production` ロックを使う。
本番 main と検証済みSHAの一致が必要。finance writer、分類・承認処理は呼ばない。

1. 合成テストとCIを通し、main統合後のCI成功SHAを既存の手順でpinする。
2. `preview`: 現状、N占有、固定支出ID整合性を読取り確認する。
3. `canary`: 最初の異なる代表IDを最大3件だけ導入する。値・数式・実際のhyperlinkを
   読戻し、会計データ・入力・保護範囲の不変を確認した後だけ `verified-v1` と記録する。
   canary段階は通常のカテゴリ更新から自動展開されない。
4. PC・iPhone Sheetsアプリ・Safariで往復する。iPhoneの直接移動ができない場合は
   Safariの代替導線も実機確認する。
5. `expand`: 検証済みcanaryが必要。対象範囲へ展開し、全リンクと不変条件を読戻す。
   再実行では変更がない場合は書込み0件となる。
6. 不一致・想定外の更新では停止し、Actionsに安全なエラーコードだけを報告する。
   自動ロールバックで本人の入力を上書きしない。

通常のカテゴリ再生成と銀行確認欄更新は同じ forward 式を同一バッチに含める。
承認更新は PR #116 と同じく B:L のみを更新する。N の明示的な導入マーカーがある
場合だけ、不足する行の式を補完し、外部変更や欠落・重複支出IDを検出すると停止する。
