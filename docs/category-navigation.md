# 代表取引確認の固定ナビゲーション

カテゴリ操作の「代表取引を見る」は、専用の閲覧シート「代表取引確認」の対象行を開く。
閲覧シートは先頭2行とA列を固定する。

- A1は「↩ カテゴリ操作の一覧へ」。縦・横にスクロールしても一覧への導線が残る。
- 各取引のA列は「↩ 元のカテゴリ操作行へ戻る」。横スクロール中も元の行へ戻れる。
- B:Mは支出明細B:Mを固定支出IDで参照し、NにそのIDを持つ。閲覧用の派生表示で、
  未送信のカテゴリ入力や承認操作はここには置かない。
- 戻り先は現在のカテゴリ操作第1ブロックのH列から完全一致で求める。同じIDの
  リンク元が複数なら「↩ カテゴリ操作の一覧へ（複数候補）」、削除済みなら
  「↩ カテゴリ操作の一覧へ（対象なし）」と明示する。共有の直前の戻り先は保存しない。
- 行番号は固定せず、各式がROWと固定支出IDから解決する。カテゴリ操作、支出明細、
  閲覧表示の並べ替えに追従する。IDの欠落・重複や他者の入力を検出した場合は停止する。
- 支出明細A:M、カテゴリ操作の入力・チェック、承認状態、銀行確認欄、既存の保護範囲を
  変更しない。旧canaryの支出明細N列は互換導線として維持する。

## 導入・検証

`Category navigation UI maintenance` は既存の `kakeibo-production` ロックを使う。
本番mainと検証済みSHAの一致が必要。finance writer、分類・承認処理は呼ばない。

1. 合成テスト、ネイティブSheetsの計算・表示検証、CIを通す。main統合後のCI成功SHAをpinする。
2. `view-preview`で読取り確認する。既存の検証済みv1 canaryの固定支出IDだけを移行対象にする。
3. `view-canary`で既存canaryの最大3件に閲覧表示を導入する。実際のリンク先、取引値、
   固定表示、不変条件を読戻した後だけ`verified-v2`にする。静的なcanary ID範囲は
   シートのメタデータに保持し、閲覧行の削除後も同じ3件を復元する。
4. PCで確認し、iPhoneのSheetsアプリでスクロール中の視認性と元の行・一覧への往復を確認する。
   PCや狭いブラウザー画面での検証をiPhone実機の確認として扱わない。Safariは未確認と報告する。
5. iPhone Sheetsの確認後に`view-expand`を実行する。検証済みcanaryと
   `iphone_sheets_verified=true`の両方が必要。全代表IDへ展開し、全リンクと不変条件を読戻す。
6. 再実行で変更がなければ書込み0件。不一致では安全なエラーコードで停止し、
   自動ロールバックで本人の入力を上書きしない。

通常のカテゴリ再生成・銀行確認欄更新は同じforward式を生成した後に閲覧シートを保守する。
固定表示、列幅、行高、戻りリンクを復元し、canary段階では対象を増やさない。
全件展開済みの`v2`段階では現在の代表ID一覧に追従し、既存の閲覧順を維持して新規IDを追加する。
承認更新は従来どおりB:Lだけを更新し、Aのforward式を維持する。
