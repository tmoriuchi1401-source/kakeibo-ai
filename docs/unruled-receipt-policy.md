# 罫線のない領収書の通常解析

所有者指定の運用ルールとして、`RECEIPT_UNRULED_POLICY=owner-unruled-v1` の場合、罫線のない画像領収書を非医療として通常の Gemini 解析へ進める。統合本番ワークフローでこの値を設定する。値が未設定・不一致なら従来の判定を維持する。

ここでいう罫線は明細表のセルを作る縦横の線。横方向の区切り線、点線、バーコードだけでは表としない。画像全体の線分から、離れた縦線2本が横線2本と交差するセルを検出する。画像を切り抜かず、EXIFの向きを補正して処理する。

文字やバーコードが多いだけで検査不能にしないよう、縦線・横線それぞれの本数ではなく、交差判定とセル比較の作業量を上限で制限する。最初の本番検証では本数上限により2枚が保留されたため、この条件を修正した。

通常の売買構造をOCRで確定できなかった場合に適用する。元のOCRと画像全体の再読2回が完了し、どの読み取りにも明示的な診療・患者・給与等の情報がなく、表罫線が検出されない画像を通す。「薬局」という店名単独は医療の根拠としない。原本に既存の医療・給与等の分類がある場合は通さない。外部送信直前にも、実際に送信する画像の同じ判定をやり直す。

これは所有者が指定した送信先の決定ルールであり、医療領収書全般の書式を保証するものではない。画像が壊れている、OCRが不完全、処理上限超過、罫線検出器が利用できない場合は新ルールで許可しない。今回の対象はPNG/JPEGで、PDFの扱いは従来どおり。

検証は合成画像による傾き・薄い表罫線・区切り線・バーコードの識別、および原OCR・再読・構造化OCRそれぞれの機微情報、既知の原本分類、送信直前の画像差し替えを含む。保留7枚の実画像でも、ネットワークを遮断してOCRから送信許可境界まで確認し、7枚すべてが通常解析へ進めることを確認した。実画像やOCR本文はリポジトリに保存しない。この検証ではGeminiへの送信、会計書き込み、原本移動は行っていない。

通常解析が許可されても、金額照合や重複防止の既存条件は引き続き適用される。Geminiの解析結果が不完全な場合には、その後の確認が必要になる。
