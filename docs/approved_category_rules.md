# 承認済みカテゴリ・ルール

## 状態と境界

この機能はコードのみ実装済みで、既定では無効です。将来分と過去分は別機能であり、次の五つは独立してすべて`false`のままにします。

- `CATEGORY_RULE_UI_ENABLED`: `カテゴリ自動分類`のモバイル向け要求表を作成・更新する。
- `CATEGORY_RULE_SAVE_ENABLED`: チェック済み要求から`カテゴリ自動分類ルール`へ保存、または無効化する。
- `CATEGORY_RULE_AUTO_APPLY_ENABLED`: 新規の未分類取込だけを補完する。
- `CATEGORY_BACKFILL_PREVIEW_ENABLED`: `カテゴリ過去反映`の候補と固定プレビューを作成する。
- `CATEGORY_BACKFILL_APPLY_ENABLED`: 確認済みの固定プレビューだけをF/Gへ反映または復元する。

通常の取込、カテゴリ対応UI、既存のF→G連動、review、重複照合、返金・振替、privacy gate、スケジュールは、このフラグがすべてfalseなら変化しません。ルール表も自動作成しません。

## 保存モデルと復元

永続的なルールの正本は`カテゴリ自動分類ルール`だけです。ルールID、条件種別、データ元、口座別名、請求名/店舗名/商品ID/商品名、任意の金額、F/G、承認元支出ID、承認日時、revision、有効状態、適用件数、最終適用支出IDを持ちます。

`カテゴリ自動分類`は要求UIであり、ルールの正本ではありません。390pxでは「対象・カテゴリ」「条件・状態」「登録する」の3列だけを表示し、支出ID・F/G・データ元・種別・承認スナップショットは非表示列で固定結合します。再生成でチェックを引き継ぐのは、その固定スナップショットが現在の条件・F/G・入力ID/状態と完全一致するときだけです。異なればチェックを外し、旧条件と現在条件を併記して再承認にします。要求を処理すると、支出IDから支出明細と元取込を再読込し、表示時のF/Gまたは条件が変更されていれば保留します。

表示状態は未登録・登録待ち・登録済み・競合・`held`（失敗理由付き）を区別する。チェックそのものは成功ではなく、再読込後の登録結果だけが状態を更新する。既存ルールの確認・無効化は正本表と`category-rule-deactivate <rule-id>`で行い、無効化は将来分だけを止める。

サービス／店舗合計の学習候補は、`auto_expense`でその支出IDへ確定済みの取込だけです。照合済み、重複、review、返金、振替、無効行は候補に出さず、登録時にも同じ検査を再実行します。

復元が必要な場合はUI要求表を削除して再生成してよいですが、ルール表は削除・再作成せず、有効列を`FALSE`にして将来分を停止します。過去の支出は巻き戻しません。

## 一致規則

- サービス: データ元＋請求名の完全一致。`bankpdf:`取込は口座別名も必須。
- 店舗合計: データ元＋店舗名、かつ商品情報のない`自動計上`/`手動計上`だけ。Amazon合計は登録しない。
- 商品: 名前空間付き商品ID、またはデータ元＋店舗名＋具体的商品名の完全一致。商品名がない取込は店舗規則へ広げない。

正規化はNFKCと空白の統一だけです。別名、接頭辞、部分一致、会社名短縮、支店統合は使いません。複数ルールが異なるF/Gを返せば保留し、同じF/Gなら一度だけ適用します。

適用対象は、承認日時より後の新規取込で、既定の`その他／未分類`に限ります。人手のF/G、既存の有効カテゴリ、商品明細、過去明細・再実行は上書きしません。適用した支出明細の備考とルール表にID/revisionを残します。

## 過去分の反映（将来自動分類とは別）

`カテゴリ過去反映`は3列表示（条件・カテゴリ／対象期間／プレビューする）です。対象期間の初期値は`ホーム!B4`の対象月で、`全期間`、開始月/終了月の`YYYY-MM..YYYY-MM`、または日付範囲の`YYYY-MM-DD..YYYY-MM-DD`に変更できます。対象日は取込日ではなく`支出明細`の日付です。保存済みルールに加え、`カテゴリ自動分類`で表示中の条件から「過去分のみ」のad-hoc要求も作れます。この経路は将来ルールを保存しません。

プレビューは`カテゴリ過去反映要求`と`カテゴリ過去反映対象`に、要求ID・条件・カテゴリ・期間・ルールID/revision（ある場合）・対象支出ID・反映前F/G・入力スナップショットを固定保存します。0件は要求を作らず反映不能です。`カテゴリ過去反映確認`で「このN件に反映」をチェックして初めて反映できます。

日常操作はこの2つのシート内で完結します。main上の`category-backfill-sheet.yml`は、専用の`CATEGORY_BACKFILL_SHEET_RUNNER_ENABLED=true`、previewフラグ、applyフラグが明示的に揃った場合だけシートをポーリングします。したがって毎回PCのCLI、ChatGPT/Codex、Gmail/Drive再取込を必要としません。runnerまたはpreviewフラグがfalseならシートを作成・変更せず、applyフラグがfalseなら確認済み要求も反映しません。

反映は対象を再検索せず、固定IDだけを再読込します。activeかつ`その他／未分類`で、対象日、F/G、取込ID・データ元・状態・店舗・金額・商品IDがプレビュー時点と一致する行だけを更新します。返金・取消・重複・照合保留・振替・チャージ・不明な状態、部分/不正カテゴリ、非active行は候補外です。サービス／店舗合計は`auto_expense`かつ同一支出IDへ結合済みの取込だけ、店舗合計は集計行だけ、商品は商品条件だけを使います。

更新範囲は`支出明細!F:G`だけです。各対象の結果・理由・反映時刻を残し、partialは同じ要求IDで再開できます。復元は「反映後のF/Gがまだ同じ」行だけを元へ戻すので、その後の人手編集を上書きしません。分類更新後にだけ`支出一覧`を更新し、表示更新に失敗しても分類結果と別に`refresh_pending`として再実行可能にします。

## 本番canary（別承認が必要）

1. UIフラグだけを有効にし、少数の手分類済み支出IDで要求表を作る。既存F→Gと390px表示を確認する。
2. 保存フラグを追加し、サービス完全一致の1ルールだけを登録する。ルール表の内容、承認元ID、初期チェックOFF、無効化を確認する。
3. 自動適用フラグを追加し、承認後に到着した1件だけを対象にpreviewとapplyを比較する。件数上限は1、停止方法は3フラグをすべてfalseに戻すこと。
4. 過去分は別承認で、runnerとpreviewフラグだけを有効にして実データの件数・金額・除外理由・対象IDをread-onlyで確認する。applyフラグはまだ有効にしない。承認後も確認シートのN件チェックが必要で、最初は1件だけを読戻しする。

各段階で、対象外の支出ID・金額・日付・計上状態・F/Gが不変であることをread-backする。承認前にUI作成、保存、自動分類を実行してはいけません。
