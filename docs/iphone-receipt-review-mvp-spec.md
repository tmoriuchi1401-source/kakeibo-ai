# KakeiboAI：iPhone領収書・PDF確認 MVP 仕様と開発方針

- **更新日**：2026-10-15
- **状態**：Google Sheetsアプリ（A方式）の合成確認UIは、ユーザーのiPhone実機評価により基本操作性を採用可能と判断。確定仕様は第10節。認証付き確定処理・本番接続の完成や承認ではなく、**デプロイ・本番書込み・PR mergeの承認でもない**。
- **適用範囲**：家計簿管理の領収書確認、PDFページ確認、医療領収書の手入力、関連するiPhone UI／認証／既存記帳処理との接続。
- **優先原則**：**iPhoneで実際に使える最小機能を早く完成させる**。ただし、医療情報の保護、二重記帳防止、原本・権限の整合性は簡略化しない。

## 1. 達成したい利用体験

家計簿の管理画面からiPhoneで未処理案件の一覧を開き、対象を選択し、Drive原本を確認しながら必要項目を修正／手入力し、本人が確定要求を送る。結果（成功、処理待ち、保留理由）を明確に確認できること。採用方式はGoogle Sheetsアプリ（A方式）とし、**PC専用メニュー／サイドバー／ダイアログに依存しない**。この段落は最終的な利用体験の目標であり、現時点で実装済みの範囲は第10節と区別する。

- 原本と入力項目を行き来しやすくする。広い画面では並列、iPhone幅では同一画面内の切替・拡大・復帰などを実機で評価。単なるDriveリンク遷移が煩雑なら「完成」としない。
- 一覧には案件種別・処理状態・要確認理由・原本リンク・最終操作結果を表示。絞り込みと戻る操作を簡潔にする。
- **操作しやすさはiPhone実機で判定**する。PCや390pxエミュレーションの成功だけでは完成扱いにしない。

## 2. MVP対象と動作

| 対象 | 最初に可能にする操作 | 安全条件 |
|---|---|---|
| 一般レシート | 原本確認、店舗・日付・支払総額・カテゴリなどの確認／修正、明示的な確定要求 | 重複照合、原本版・入力版・本人承認を検証し、既存writerのみ利用 |
| 医療領収書 | 施設名・支払日・**実際の支払額**・カテゴリ等を原本を見て**完全手入力**、確認／確定 | 医療情報を外部AIへ送信しない。AI/OCR候補の自動採用をしない |
| 複数ページPDF | ページ順・種類・区切り・分割／結合候補を確認し、明示的に判断 | 全ページのprivacy gateを維持。構造確定と記帳許可を混同しない |
| 既存記帳との重複疑い | 新規原本と既存明細を比較し「同一／別／判断不可」を選択 | 「同一」は既存明細へのリンクであり、追加記帳しない。「別」も自動記帳許可ではない |

初期MVPでは未対応のpurposeを「保留／未対応」と明示し、推測で処理を進めない。医療と一般が混在するPDFを一括で一般扱いしない。複数ページの`grouping_required`は既存の明示確認が満たされるまで停止する。

## 3. 実装方式の方針（A方式採用済み・過剰実装しない）

1. **A：Google Sheetsアプリ改善を採用する**。ユーザーのiPhone実機評価で基本操作性を採用可能と判断し、第10節のUIを確定した。元画面・原本リンク・入力規則を再利用し、PC向けApps Scriptメニュー等に依存しない。既存処理を再利用する方針は維持するが、安全な確定要求・本番記帳との接続は未実装・未承認である。
2. Aで今後具体的な未達条件が判明した場合に限り、**B：Apps Script Webアプリ**の再評価案を提示する。妻を含む許可ユーザーのGoogleアカウントを確実に識別できるか、実行者権限・所有者実行時のID取得制約を検証する。**Apps Scriptが既存Python validator／writerを直接呼べるとは仮定しない**。安全な接続先がなければ再設計する。方式や確定UIを事前承認なく変更しない。
3. A/Bで達成できない具体的な要件がある場合、**C：既存Python＋Cloud Run**の再評価案を提示する。既存のstaging検証・認証ホストコードの再利用余地はあるが、IAM・egress・本番アクセス防止の未解決ゲートを飛ばさない。Cloud作業の凍結は継続し、再評価や実施を自律的に再開しない。

選定基準：iPhoneでの操作回数／原本の見やすさ、既存validator・writer再利用率、認証・秘密情報の扱い、開発期間、継続費用・保守負担。**最も簡単な方式が必要条件を満たすなら、追加サーバーを作らない**。逆に、操作性や権限安全性を損なうためだけにSheets方式へ固執しない。

## 4. 変更してはいけない安全境界

- **表示（GET）はread-only**。ページ表示によって観測、CAS、authority、会計書込み、AI送信、原本移動を発生させない。
- 画面から会計明細への**新規の直接書込み経路を作らない**。既存の目的別validator／authority／writer、重複・replay保護、revision一致、read-back、CASを再利用する。
- `STRUCTURE_REVIEW`、`METADATA_REVIEW`、`RECONCILIATION_REVIEW`、`ACCOUNTING_POST`を分離する。種類や分割・結合の確定だけでAI送信・記帳・移動を許可しない。
- 原本ID/hash/version、安定したpage identity、Unit/index、入力snapshot、purpose、操作主体と既存明細照合を新旧画面で整合させる。類似する日付・金額・ファイル名だけで旧案件を再結合しない。
- `LEGACY_UNMAPPED_HOLD` の旧医療案件は**表示／保留のみ**。紐付けを推測せず、authority移植、再記帳、自動リトライ禁止。他の新規案件の開発まで全面停止させない。
- 医療領収書は**完全手入力**、外部AI送信禁止。PDFのmedical/unknown等に一般レシート送信許可を流用しない。
- 認証：Google本人認証に加え、許可されたowner（必要なら妻を明示許可）の認可、session、Origin/CSRF、要求期限、リクエスト再送防止を既存経路と整合。公開URLがあってもログイン／所有者確認を省略しない。
- credentials、医療画像、原本snapshot、監査データはGit・PR・CI成果物・外部AIへ出さない。Secretsや既存本番のCloud設定を流用しない。
- `UNIFIED_RECEIPT_WRITE_ENABLED`を既定OFFのまま維持。構造、種類、プライバシー判断と金融的なPOST許可を別ゲートで扱う。

## 6. 開発順序とゲート

### Gate 0：方式選定・基本操作性の採用判断済み
- A/B/Cの比較とユーザーのiPhone合成UI実機評価を経て、A方式を採用した。再開時に方式選定からやり直さず、第10節を引き継ぐ。
- この採用判断は認証・既存処理接続・本番記帳の安全性や完成を認定しない。**Cloudの未確認項目を無期限に調査しない**。

### Gate 1：synthetic UIと安全なread-only導線
- 案件一覧・原本リンク／表示・入力／確認・保留理由・処理結果を合成データで操作する。
- iPhone実機で一般／医療／PDFの画面遷移を確認。未対応の確定操作は無効・理由表示。外部AI・金融write・原本移動は0。
- 現在は第10節の固定4タブの基本操作性についてユーザー採用判断済み。複数案件の動的表示や確定要求の送信・処理結果連携まで実装済みとしない。

### Gate 2：認証された既存処理への接続
- 選定方式でGoogle認証、owner判定、原本／入力の新鮮性、purpose別の既存validationを接続。
- 実write・原本移動は引き続き別途承認。stale、duplicate、replay、同時操作、失われたレスポンス、誤操作でfail-closedを検証。

### Gate 3：実データcanaryと本番導入（**別途承認必須**）
- 新規の正常な**一般**原本1件を優先。旧未対応医療案件の再利用は禁止。既存writerの完全な権限／read-backが確認できないなら未実行。
- 記帳件数／重複／原本移動／AI送信／authority変化を監査し、期待外なら停止。医療・混在PDFの実運用は別に許可を得る。
- iPhone Safari/Sheetsアプリの実機結果を確認してから、入口切替・旧確認シート整理・main mergeをそれぞれ承認する。

## 7. 完了条件（「使える」と呼ぶための基準）

- iPhoneから一覧→原本確認→必要な入力→明示確定／保留→結果確認まで迷わず操作できる。
- 一般・医療・PDFで、分かる保留理由と次の行動が表示される。未対応なら「未対応」と表示し、成功を装わない。
- 一般レシートの正しい会計反映は既存writerとledger read-backで確認。再送・重複による**余分な記帳0**。
- 医療の外部AI送信**0**、原本／個人情報の意図しない露出**0**。
- stale snapshot・identity不一致・権限なし・不確かな結果は**fail-closed**。
- 本番反映前の許可されないwrite／原本移動／authority変更**0**。
- iPhone実機（本人、必要なら妻の許可済みアカウント）で動作確認済み。PC／CI／390pxのみでは完成としない。

## 10. iPhone UI確定仕様（2026-10-15・ユーザー実機評価に基づく決定）

### 10.1 採用判断と適用範囲

**採用方式はGoogle Sheetsアプリ（A方式）**。完全合成データの独立検証ブックについて、ユーザーのiPhone実機評価と表示調整後の承認により、基本操作性は採用可能と判断した。この決定を今後の開発の基準にする。

評価結果の根拠はユーザーの実機フィードバックであり、CodexがiPhoneを直接操作したという記録ではない。iOS／Sheetsアプリの正確なバージョン、タップ数、通信切断・再認証を含む入力復帰の網羅試験、Safariの操作結果は確認済みとしない。合成UIの採用を、実データの確定成功やシステム全体の完成と混同しない。

### 10.2 固定するUI設計

| 項目 | 確定仕様 |
|---|---|
| タブ構成 | 「一覧」「一般」「医療」「PDF」の4タブを維持する。用途別のタブであり、案件数に比例してタブを増やさない。 |
| 列幅 | 医療タブを表示基準とする。現在承認済みのA列80px・B列208px、合計288pxを維持する。一般・医療・PDFは同一設定。途中で試したA列108px・B列220px（計328px）の案は最終採用値ではない。一覧の既存表示設定も維持する。 |
| 文字・余白 | 現在の指定フォントMeiryo・本文11pt、左右余白3px、縦中央を維持する。極端な文字縮小や、画面に合わせるためだけの追加の幅縮小をしない。 |
| 折返し・行高 | セル内の折返し（WRAP）を維持する。説明・入力・原本名詳細に必要な既存の行高を保つ。入力や選択肢を隠さない。 |
| ブック内移動 | 下部タブを使用する。Safariが開く同一ブック内のフルURLリンクを復活させない。セル内のタブ案内文をリンクや送信ボタンと誤認させない。 |
| 原本確認 | 既存のGoogle Drive原本リンクを利用する。「外部原本」として、下部タブによるブック内移動と区別する。 |
| 原本名 | PDFの長い原本名は短縮表示し、全文を同じタブ下部の詳細欄に残す。 |
| 案件の区切り | 案件ID・見出し・外枠・終了位置を明示し、別案件の入力欄と混同させない。 |
| 入力途中の値 | タブ移動・画面再表示・UI更新で保持する。入力済みの値や選択を初期化しない。入力規則・原本リンク・保留状態も保持する。 |
| 一般 | 原本を確認しながら、日付・店舗・金額・カテゴリ等を修正できる。 |
| 医療 | 日付・施設・実支払額・カテゴリ等を完全手入力する。OCR・AI候補の採用や医療情報の外部AI送信を行わない。 |
| PDF | ページの分割位置・結合範囲を選択できる。現在の検証ブックでは選択値を保存するだけで、実際のPDF加工・Receipt Unit作成・記帳許可には接続しない。 |

検証ブックのセル入力や「練習確認」の選択だけで、新たなauthority、送信許可、記帳許可を成立させない。実際の旧p1の`LEGACY_UNMAPPED_HOLD`は引き続き隔離し、合成保留カードの操作と混同しない。

### 10.3 未実装・未承認の事項

以下を今回のUI採用判断に含めず、完成済み・実行承認済みとして記録しない。

- 本番記帳処理との接続。
- 本人と妻の2名の認証・認可を伴う確定処理。Google Sheetsで編集できることだけを確定権限の証明にしない。
- 複数案件を4タブ内へ動的に表示する仕組み。
- 本番データを使った確定検証・実データcanary。
- PR #123／#124のmain統合。

今後の接続では、既存Python validator／writer／authority、duplicate・replay・revision・CAS・read-back・privacy gateを維持する。新UIから会計明細へ直接書き込む経路を作らない。

### 10.4 今後の変更と安全ゲート

確定済みUIを変更する必要がある場合は、**変更理由、変更対象、影響範囲、既存入力・入力規則・原本リンク・操作性への影響、検証方法を示し、変更前にユーザーの承認を求める**。承認なしにタブ構成・列幅・表示設定・移動方式を再設計しない。

今回の仕様書更新はMarkdownのみを対象とし、検証ブック・本番Spreadsheet・記帳処理・authority・writerは変更しない。Cloud Run関連作業は停止したまま、PR #123／#124はDraft維持、mainへのmergeは禁止。本番接続・会計write・原本移動・AI送信・実authority発行／更新は、引き続き個別の承認範囲に従う。

以前の方式選定・UI再評価の記述と矛盾する場合は、この第10節の確定仕様を優先する。ただし、既存の安全条件や未承認事項を緩和する根拠にはしない。
