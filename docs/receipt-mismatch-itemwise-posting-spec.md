## 1. 決定した基本原則

1. **レシート1枚を1カテゴリ・1支出行に潰さず、商品などの会計明細ごとに分類・記帳する。** レシート単位の支払総額は照合の基準とし、同じ支払いを商品行と総額行で二重計上しない。
2. 人間に要求するのは**システムが解決できない例外の確認・最小限の修正**のみ。商品別カテゴリは既存の承認済みルール・商品マスタ・解析候補を再利用し、既に確定した項目を再入力させない。
3. **金額の一致は必要条件だが十分条件ではない。** レシート原本の根拠、商品明細、税・値引き、カテゴリ、重複、本人入力と原本版の整合性も検証する。差額だけを合わせる架空の「調整」「その他」行は作らない。
4. **セル編集は下書きの保存にすぎない。** 「修正内容を登録する」の明示操作で処理要求を発行し、認証・認可された既存validator／authority／writerで処理する。通常時に取引ごとの追加の本人承認操作を要求しない。バックエンドの安全ゲートや本番導入の別途承認は省略しない。
5. 採用済みの**Google Sheetsアプリ（A方式）・「確認」1タブ／1行＝1案件**を維持する。案件を開いた先で複数の商品明細を確認・編集する設計とし、商品ごとの別案件タブや新たなWebサーバーを既定としない。旧「要確認」タブは移行前の既存画面として扱う。

## 2. 2つの金額の定義・表示

| 表示名 | 定義・算出方法 | 確認の意味 |
|---|---|---|
| **レシート支払総額** | AIが画像中の支払総額欄から抽出した `result.total`。取得直後は**解析候補**であり、原本と照合して初めて本人確認済みとなる。 | 実際の支払総額。原本に対する確認結果は同一の原本ID/hash/versionと入力版に結び付けて保持する。 |
| **読取明細の合計** | AIが抽出し保存した個々の明細 `item.amount` を、システムが整数円で合算した `sum(item.amount)`。商品に加え、明細として読み取った外税・値引き等を含み得る。 | **読み取れた範囲の合計**であり、明細の漏れ・誤読があると支払総額と異なる。 |
| **差額** | `レシート支払総額 - 読取明細の合計` | 正なら明細合計が不足、負なら明細合計が超過。差額自体は商品の存在や原因の証拠ではない。 |

不一致時の文言は、用語だけの「解析合計」「補○円」「原本と未計上の解析候補明細の合計を確認」を避け、**出所→計算→状態→次の操作**を示す。

**表示例A（今回確認済みの総額）**

> ⚠️ 商品明細の合計が138円不足しています（未記帳）  
> 🧾 レシート支払総額：**1,368円** — AIが合計欄から読み取り、本人が原本と照合済み  
> 🛒 読取明細の合計：**1,230円** — AIが読み取った各明細をシステムが合算  
> 差額：**+138円**（1,368 − 1,230）  
> 商品・税・値引きの読取漏れや金額誤読の可能性があります。**原因は未特定**です。自動再照合で解決できなかった箇所を確認してください。  
> ［原本を見る］［解析した商品明細を見る］

**表示例B**：レシート支払総額967円、読取明細の合計939円、**差額+28円（不足）**。両方とも原本に対する支払総額は本人確認済み。ただし、**内訳まで確認済みとみなさない**。

- 解析候補と本人確認済みの値を混同しない。本人確認済みの支払総額は、同一版では再質問しない。原本の版変更・照合対象変更・本人入力の変更時は確認状態を再検証する。
- リンクの原本と候補行は同じ取込ID・解析hashに結び付ける。保存済み候補が一致しない、欠落、他案件に紐付く場合はリンクや金額を捏造せず「照合資料に不整合／保留」とする。
- iPhoneではまず支払総額・明細合計・差額・現在の状態・次の操作を見せ、技術的な根拠や明細全件は展開先で見せる。既存タブに大量の列を増やさない。

## 3. 通常時と不一致時の自動処理

1. 一般レシートとしてのprivacy gate・原本identity検証に合格した場合だけ解析する。**医療は完全手入力、外部AI送信禁止**。
2. AIが商品名・数量・金額、明示された税・値引き等を抽出する。レシート支払総額とは別に明細合計を**プログラムで計算**する。
3. 不一致なら、既存の自動再読取方針（同一原本を最大3回まで）と原本上の根拠を使い、商品抜け、数量・金額の誤読、外税、値引き・支払手段を再照合する。画面閲覧や入力保存だけで無制限の再解析はしない。
4. 商品別に既存の商品マスタ、承認済みの**商品単位**分類ルール、AI解析結果を利用する。矛盾する分類根拠を無理に自動確定しない。店舗・決済単位のルールを複数商品の全行に一括適用しない。
5. 明細合計、カテゴリ、原本根拠、重複、安全条件が成立するなら既存の記帳経路へ進む。**合計不一致・未解決の税/値引き・構造不明は記帳保留**。
6. カテゴリ候補が存在しないだけなら、既存マスタの「その他／未分類」を商品行ごとに使用できる場合は商品別内訳を保持し、後続の「カテゴリ対応」に残す。**候補間の矛盾**や税・値引きの分類配賦が不明な場合は、恣意的に未分類で確定せず保留する。明細金額の不一致をカテゴリの問題で上書きしない。

## 4. 人間が修正する操作（AIが解決できない場合だけ）

**iPhoneの想定操作**：

1. 「確認」で対象案件を選択する。原本リンクと解析した商品明細、支払総額・明細合計・差額・原因候補を表示する。**疑わしい行は根拠がある場合のみ**強調する。特定不能なら「原因不明」と表示する。
2. 原本と比較し、**必要な明細だけ**変更する（次表）。既に本人確認した支払総額は同じ版で入力し直さない。
3. システムが表示中の修正後明細合計・差額を再計算する。数値が一致しても原本根拠と商品/税/値引きの整合性は別途バックエンドで検査する。
4. ユーザーが**「修正内容を登録する」**を1回押す。後続は §5 に従い検証・記帳・結果表示する。判断できなければ「保留」し、入力を保持する。

| 原因 | 人間の修正操作 | 禁止／注意 |
|---|---|---|
| 商品名・金額の誤読 | 元の明細行の名称／金額を原本どおり修正 | 差額だけを合わせる編集は禁止 |
| 数量の誤読 | 数量を原本で確認・修正し、金額との関係を検証 | 現行コードの数量変更は未対応。追加実装・テストが必要 |
| 商品の読取漏れ | **原本にある商品**を商品名・数量・金額付きで1行追加 | 現行コードは商品数固定。IDと原本根拠を伴う追加機能が未実装 |
| 二重抽出・存在しない行 | 根拠を比較し、重複／誤抽出行を除外 | 現行コードは商品数固定。既存明細IDの誤転用を禁止 |
| 外税・値引きの読取漏れ | レシートに明記された税・値引きの行または商品への帰属を確認 | 内税の二重加算、根拠のない配賦、架空の差額補正は禁止 |
| 原本を見ても原因不明 | **保留**して入力・原本を保持 | 支払総額だけの暫定1行記帳、推測した商品の作成を今回のMVPには追加しない |

例：AIが商品Bを330円と読んだが原本は468円なら、**商品Bのみ468円に修正**する。明細合計1,230円→1,368円、差額138円→0円。**これは操作説明の仮例であり、今回の実レシートで商品Bが誤読された証拠ではない。**

既存の明細ごとの修正機能は再利用するが、**商品行の追加・除外・数量修正や「要確認」からの接続を実装済みとは扱わない**。

## 5. 保存／登録／記帳のタイミングと状態

| 段階 | 発生タイミング | ユーザーに見せる状態 | 会計write |
|---|---|---|---|
| 下書き保存 | セルを修正したとき | 「編集中／未登録」 | **0件** |
| 確定要求の受付 | 「修正内容を登録する」を押したとき | 「受付済み」 | **まだ0件** |
| 既存バックエンドによる検証 | 受付後のGitHub Actions等の処理で実行 | 「検証中」→結果 | 権限なしなら**0件** |
| 検証成功・記帳許可あり | 既存authority／validated SHA／ledger／重複等の全条件が成立後 | 既存writerが商品行を登録し、独立read-back成功で「記帳完了」 | 商品行のみ、**二重計上0件** |
| 検証成功・記帳許可なし／NO-GO | 登録要求処理時 | **「検証済み・未記帳」** | **0件** |
| 入力不備・金額不一致・カテゴリ競合等 | 検証で検出 | 「修正が必要／保留理由」 | **0件** |
| 書込み成否不明・競合・stale | 応答喪失や整合性不成立 | 「結果不明・照合待ち」 | **再送禁止** |

- **通常時は次の定期実行を待たず**、登録要求に応じて処理開始する。GitHub Actionsの待ち時間は保証しない。「受付済み」を「記帳完了」と表示しない。
- **通常の取引ごとの追加承認操作は要求しない**。ただし、既存backendが必要とする操作主体の認証、明示要求、期限、専用authorityや本番rolloutの承認をUI操作で迂回しない。
- NO-GO・write OFF時は、UI登録で本番writerを起動しない。後日フラグが変わっただけで、古い「検証済み・未記帳」を**自動記帳しない**。再開には新鮮な状態・authorityでの明示的かつ安全な再要求／照合を必要とする。
- 異常・UNKNOWNの自動retryは禁止。完成した商品別記帳は台帳・支出一覧で正確にread-back後、同じ画面へ結果を返す。画面更新失敗を二重記帳の理由にしない。

## 7. 実装の優先順位と受け入れ条件

**最小順序**：①金額の出所・差額・状態の説明改善 → ②保存済み候補と商品別分類の連携 → ③自動再照合と、未解決商品の編集（必要時の商品追加・除外・数量修正） → ④明示的な1回の登録要求→既存writer→read-back。

必須の合成テスト：
- 不一致例 **1,368円−1,230円＝+138円** と **967円−939円＝+28円** を誤解なく表示する。本人確認済み総額は同一版で再質問しない。
- 商品名・金額誤読、数量誤読、商品欠落、二重抽出、税・値引き、分類ルール競合、カテゴリ不明、原本変更、候補hash不一致を区別する。
- 差額だけの架空明細を拒否。税／値引きの二重計上・根拠なき多カテゴリ配賦を拒否。
- 入力保存だけの会計write **0**。本人の1回登録要求、重複・replay・同時更新・stale・UNKNOWN時の重複write **0**。
- ledger/authorityがNO-GOなら「検証済み・未記帳」で停止し、フラグ変更だけでは記帳しない。
- 一般の許可原本以外にAI送信しない。医療は完全手入力。iPhone実機で案件選択→原本→修正→登録→状態確認を検証する。

**禁止範囲**：この仕様文書作成によるmain更新、GitHub Variables／Secrets／workflow dispatch、本番Sheets・台帳・原本・authorityの変更、AI送信、原本移動、実金融writeは**いずれも行わない**。処理コード変更・main merge・本番適用は独立した段階で実施し、既存NO-GOと承認ゲートを維持する。
