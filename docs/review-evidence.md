# 要確認の判断材料

2026-09-26 時点のコードと「家計簿 管理」の読取調査に基づく棚卸し。通常の `要確認` は `取込データ` の処理状態から生成される。実データで現在この一覧に残るのは receipt 2 行。別の確認画面には `分類・ルール承認` 86 件、`分類・過去分反映` 2 件、`領収書確認` 2 件がある。`Amazon要確認（旧・保管）` は現行の判断導線ではない。

| 確認種別 / status または data_type | 判断と比較 | 現在の材料 | 一覧からのアクセス |
| --- | --- | --- | --- |
| receipt `要確認` | 抽出した日付・店舗・金額・解析結果と原本の印字を比較 | `取込データ` 行、Drive原本 | `要確認` G の「原本を開く」。ファイルIDで開くため `receipt_inbox` から `processed` への移動後も同じリンク |
| `needs_review_duplicate` など重複疑い | 新規取込と既存明細または関連取込を比較 | `取込データ`、`支出明細`、備考中の明示的な候補ID | G から正確な取込行。確定した `target_id` があれば H から該当行。候補が1件なら H から候補行、複数なら H から `確認材料` の該当候補一覧へ移り、各候補行・レシート原本を開ける。候補IDは実在行と照合する |
| `amazon_needs_review` / `needs_review_amazon_installment` / `amazon_unmatched` | カード取込と注文候補、元利用、請求内訳を比較 | `取込データ`、同じ行の候補欄、`Amazon照合候補` | G から取込行。候補が生成される構成では H から同じ確認行の候補欄。候補がなければ明示。金銭確認モードの Amazon は専用の日常画面へ誘導 |
| `needs_review_refund` / `needs_review_transfer` / 銀行PDF由来の判定 | 返金・資金移動の取込と元取引、元明細を比較 | `取込データ`、存在すれば `target_id` の行、銀行PDF | G から正確な抽出行。H は `target_id` を解決できるときのみ。銀行PDFのDrive file IDは取込行に保持されていないため、PDF原本へのリンクは生成しない |
| `分類・ルール承認`、service 条件 | 条件と現在・候補カテゴリ、代表取引を比較 | `カテゴリ操作` の条件・カテゴリ、`支出明細` の代表ID | 条件・カテゴリは行内。A の「代表取引を見る」から代表IDに対応する正確な支出行 |
| `分類・過去分反映`、previewed / confirmed / partial | 元ルール、現在カテゴリ、反映候補を比較 | `カテゴリ操作` の条件・対象行・現カテゴリ・候補カテゴリ | 確認ブロック内に対象行と差分を並べる。行内にある比較情報への余分なリンクは増やさない |
| `領収書確認`、一般 / 医療 / 受付保留と各 reason | 原本と既存値・解析候補、必要時は本人入力を比較 | `領収書確認` の原本URL・理由・既存値・候補値 | 既存の同一行表示とDrive原本リンクを利用。機微情報の送信先は追加しない |

## 共通実装

`ReviewResource` は `label`、`role` (`target` / `comparison` / `supporting`)、`resource_type` (`drive_file` / `sheet_range`) と実際の識別子を持つ。DriveはファイルID、シートは spreadsheet ID・sheet ID・対象範囲でリンクを作る。存在が確定していない比較先は推定でつながない。通常の `要確認` は理由に応じて G/H の最大2件を選び、候補が複数あるときだけ候補一覧を生成する。既存の判断・承認欄は右へ1列移し、旧20列と21列の入力を移行時に維持する。

スマホでは短いリンク文言をタップして原本または対象行に移る。リンクの実際のiPhone版Google Sheetsでの開き方は端末側のアプリ設定にも依存するため、公開後に実機で確認する。

## 制約

銀行PDFの `bankpdf:` 取込IDはDrive file IDではない。元PDFへの一タップを実現するには、原本の file ID を安全に保存する取り込み側の追加変更が必要。別の取引を日付・金額だけで推測して比較リンクにすることはしない。
